### 1. Как обеспечивал сервинг моделей? Какие инструменты и платформы использовал?  
   Ответ: 🍀 Сервинг LLM обеспечивал через **vLLM и Ollama**, развёрнутые в **Kubernetes**, с использованием **GPU (A100/H100)**, и **MIG**.  

  Почему vLLM:
  
  * PagedAttention → экономия GPU памяти  
    - Как у аналогов: Выделяют под этот кэш непрерывный кусок памяти «с запасом» под максимальную длину max_seq_len. В итоге до 60–80% видеопамяти тратится впустую (фрагментируется или резервируется под неиспользованные токены).  
    - Как в vLLM: Память выделяется динамически небольшими блоками, как виртуальная память в операционных системах. Фрагментация падает почти до нуля (менее 4%), что позволяет уместить в одну видеокарту в разы больше параллельных запросов (батчей).
  * Есть Continuous Batching
    - vLLM умеет подсаживать новые запросы в батч и высаживать завершенные прямо на уровне генерации отдельных токенов (iteration-level scheduling). Видеокарта всегда загружена на 100%.
  * Хорошо масштабируется
  * Отлично работает с MIG
  * Поддержка OpenAI-compatible API
  
  Архитектура сервинга (типовая)

```
Client
  ↓
Ingress / Load Balancer
  ↓
LLM API Service
  ↓
vLLM Pods (GPU / MIG)
  ↓
Model Weights (PVC / local SSD / NVMe)
```  

  > 🍀 Конкретно я хранил веса на локальных NVMe внутри кластера, используя в k8s тип PV `local`, так как это обеспечивало быстрый старт модели (40Гб весов загружались в память GPU примерно за 10 секунд), по сравнению с сетевыми хранилищами (там веса загружались 10 минут). Это позволяло быстро начать обрабатывать запросы.

### 2. Как следует версионировать LLM модели в продакшене?  
  Ответ: **Схема именования (Best Practice):**  

Используйте расширенный [SemVer](https://semver.org/lang/ru/) или кастомные теги:  
```production-v2.1-llama3-8b-awq-p42```  
`v2.1` — версия вашего сервиса.  
`llama3-8b` — изначальная модель.  
`awq` — тип оптимизации. (Activation-aware Weight Quantization): Один из самых эффективных форматов для GPU. Сохраняет высокую точность при сжатии до 4 бит. Отлично поддерживается в vLLM.  
`p42` — ID системного промпта.  

**Деплой (Blue-Green / Canary)**  

- Никогда не меняйте модель «на горячую». Из-за недетерминизма новая версия может начать «галлюцинировать» там, где старая работала.
- Запускаете Shadow Deployment (трафик идет в обе модели, но ответ пользователю дает старая).
- Сравниваете ответы (LLM-as-a-judge).
- Постепенно переключаете трафик (Canary).

### 3. Как непосредственно для тебя выглядит публикация новой модельки? Ты садишься за ноут и что делаешь?

**Ответ:** 🍀

1. **Подготавливаю артефакты модели**

   * тяну веса с HuggingFace (в формате safetensors / GGUF);
   * при необходимости — беру квантованные версии;
   * проверяю совместимость с runtime (vLLM / llama.cpp и т.д.).

2. **Сохраняю модель в Registry**

   * храню веса и все связанные файлы модели в **Nexus Registry**;
   * версия модели фиксируется явно (model + версия + квантизация).

3. **Деплой на инфраструктуру**

   * загружаю веса на хост;
   * примонтирую их в Kubernetes через **volume / PVC** (используя тип PV `local` для NVMe);
   * за счёт этого контейнеры остаются лёгкими, а модель можно обновлять независимо от image деплоймента.

4. **Обновляю конфигурацию inference-слоя**

   * описываю новую модель в конфиге **LiteLLM Proxy**:

     * путь к весам,
     * backend,
     * параметры генерации,
     * метаданные (название, версия, теги).

5. **Настраиваю доступ**

   * Python-скриптом через API LiteLLM задаю нужные **группы / права доступа** (в OpenWebUI и LiteLLM Proxy);
   * после этого модель автоматически появляется в **OpenWebUI** для нужных пользователей или команд.

6. **Проверяю работоспособность**

   * делаю smoke-тесты через API;
   * проверяю latency, ошибки, корректность ответов;
   * убеждаюсь, что старая версия при этом остаётся доступной.
  
7. **Если всё ок → начинаю постепенный rollout (Canary) и мониторю метрики (TTFT, TPS, LLM-as-a-judge).**

### 4. Как через API LiteLLM Proxy получить список доступных моделей?

Пример **Python-кода**, который показывает, как через API **LiteLLM Proxy** получить список доступных моделей:

```python
import requests

# URL LiteLLM Proxy API
API_URL = "http://localhost:8080/v1/models"  # меняем на ваш хост/порт

# Если требуется авторизация через API key
HEADERS = {
    "Authorization": "Bearer YOUR_API_KEY_HERE",  # если используется
    "Content-Type": "application/json"
}

def list_models():
    try:
        response = requests.get(API_URL, headers=HEADERS)
        response.raise_for_status()
        data = response.json()
        
        # Пробежимся по моделям
        for model in data.get("models", []):
            name = model.get("name")
            version = model.get("version", "N/A")
            status = model.get("status", "unknown")
            print(f"Model: {name}, Version: {version}, Status: {status}")
            
    except requests.exceptions.RequestException as e:
        print("Error while fetching models:", e)

if __name__ == "__main__":
    list_models()
```
**Что делает код:**

1. Подключается к LiteLLM Proxy API `/v1/models`.
2. Отправляет GET-запрос с заголовками (API key, если нужно).
3. Получает JSON с описанием моделей.
4. Выводит на экран имя модели, версию и статус (загружена/не загружена).

### 5. Что такое GitOps подход?

**Ответ:** GitOps — это подход к **управлению инфраструктурой и приложениями через Git** как единственный источник правды.

**Как работает GitOps?**

1. Всё состояние инфраструктуры и конфигураций хранится в Git репозитории.
2. Специальные агенты (ArgoCD / Flux) **сравнивают Git с текущим состоянием кластера**.
3. Если есть расхождение → автоматическое приведение к состоянию из Git.

---

**Основные принципы GitOps**

* **Git как source-of-truth** — всё изменение проходит через коммит.
* **Автоматизация через контроллеры** — ArgoCD синхронизирует кластер.
* **Прозрачность и аудит** — все изменения видны в Git.
* **Rollback через Git** — откат изменений делается коммитом, не руками.

---

**🍀 Пример использования GitOps в Kubernetes**

* Я пушу новый Deployment с моделью в Git (например, манифест LiteLLM Deployment).
* ArgoCD видит изменения → автоматически применяет их в кластере.
* Проверяю через OpenWebUI / API, что новая модель доступна.

### 7. Какие форматы хранения LLM моделей бывают?

Ответ:

1. **PyTorch / Hugging Face (.pt / .bin / .safetensors)**

   * Стандартный формат весов для моделей PyTorch.
   * `.safetensors` — безопасный бинарный формат без возможности выполнения произвольного кода.

2. **TensorFlow / Keras (.ckpt / SavedModel)**

   * Форматы для TensorFlow-моделей, можно сразу деплоить в TF Runtime.

3. **ONNX (.onnx)**

   * Универсальный формат для моделей, позволяет переносить между фреймворками.
   * Подходит для оптимизации и инференса на разных бэкендах (CPU, GPU, TensorRT).

4. **GGUF / GGML / GPTQ / Q8 / Q4**

   * Квантизованные форматы для ускоренного инференса на ограниченных ресурсах.
   * Используются для локальных LLM (LLaMA, MPT, Mistral) с LiteLLM / vLLM.

5. **TensorRT / Torch-TensorRT / Triton Optimized**

   * Оптимизированные для GPU, часто используют для продакшен-сервинга больших моделей.

6. **llama.cpp / GGUF / GGML (C-подобные форматы)**

   * Для запуска моделей на CPU и локальных системах.
   * Поддерживают квантизацию и оптимизацию для лёгкого инференса.

### 8. Что такое квантизация моделей и как она влияет на качество?
Ответ:

**Квантизация (Quantization)** — это **процесс снижения точности весов нейросети (перевод их из чисел с плавающей точкой высокой разрядности в более простые, компактные форматы)**.  

Если упростить: это **архивация модели**, которая делает её «легче» и быстрее, но может привести к потере нюансов.  
#### Как это работает?
Обычно модели обучаются в формате **FP32** (32 бита на число) или **FP16**. Квантизация переводит их в **INT8** (8 бит) или даже **INT4** (4 бита).  
 - Вместо того чтобы хранить число `0.12345678`, модель хранит условное `0.12`.
 - Это позволяет сократить размер модели в 4–8 раз. Модель, которая занимала 40 ГБ VRAM, после квантизации в 4 бита «влезает» в 10–12 ГБ.  

#### Как это влияет на качество?

Важно понимать метрику **Perplexity** (непредсказуемость модели). При квантизации она растет (это плохо), но степень влияния зависит от метода:  

1. **4-bit** (Золотой стандарт): Потеря качества практически незаметна для человеческого глаза (обычно 1–3%). Это «бесплатный обед»: вы экономите 75% памяти, почти не теряя в интеллекте.
1. **2-bit / 3-bit**: Здесь начинается деградация. Модель может начать путать факты, чаще ошибаться в коде или «зацикливаться» на словах.
1. **Влияние на логику**: Сильнее всего квантизация бьет по сложным математическим задачам и строгому следованию формату (например, выдаче чистого JSON).

#### Популярные методы квантизации:

 - **Post-Training Quantization (PTQ)**: Берем готовую модель и сжимаем её. Быстро, но есть риск потери качества (примеры: **GPTQ, GGUF**).
 - **Activation-aware Weight Quantization (AWQ)**: Умное сжатие, которое определяет «важные» веса и не трогает их, сжимая только второстепенные. Качество выше, чем у GPTQ.
 - **Quantization-Aware Training (QAT)**: Модель «учится быть сжатой» еще в процессе обучения. Самый точный, но самый дорогой метод.

### 9. Где используется косинусная близость в LLM?

Ответ:

**Косинусная близость** используется при сравнении эмбеддингов — в retrieval, semantic search, re-ranking и обучении embedding-моделей. В **Attention механизме** используется **Dot-product** (Скалярное произведение), который при нормализации эквивалентен косинусной близости.

**Что и когда используют в LLM и поиске (RAG)?**

**Косинусную близость** используют, когда длина документов в базе данных сильно отличается (есть короткие статьи и длинные тексты). Она гарантирует, что длинный документ не победит в поиске только за счет своего объема.

**Dot product (Скалярное произведение)** используют, когда все векторы в базе знаний имеют строго одинаковую длину (так называемые нормализованные векторы, у которых длина равна 1). Если векторы нормализованы, то Dot product становится математически равен косинусной близости. При этом Dot product считается процессором компьютера в разы быстрее, потому что не нужно тратить ресурсы на деление и вычисление корней.

### 10. За какими метриками и параметрами модели нужно следить в продакшене? Как следить за качеством ответов и дрифтом?

Ответ: Мониторинг в продакшене делится на три уровня: **инфраструктурный** (здоровье железа), **инференс** (скорость ответов) и **семантический** (качество ответов).

#### 1. Технические метрики (Performance & Infrastructure)
Это базовые показатели, которые говорят о том, насколько эффективно модель использует ресурсы.
- **TTFT (Time to First Token)**: Время до выдачи первого токена. Самая важная метрика для UX — если она > 1-2 сек, пользователь чувствует «тормоза».
- **Tokens Per Second (TPS)**: Общая пропускная способность.
- **TPOT (Time Per Output Token)**: Среднее время генерации каждого последующего токена.
- **VRAM KV-Cache Usage**: Заполненность кэша контекста. Если кэш забит, новые запросы встают в очередь (Queue Delay).
- **Model Latency vs Request Length**: Зависимость скорости от длины промпта (помогает выявлять аномалии в длинных контекстах).
- **CPU/GPU utilization, Memory/VRAM usage, Disk I/O**: Классические метрики для выявления узких мест в инфраструктуре.
- **Error rate (5xx, timeouts)**: Если растет, нужно срочно смотреть логи и состояние кластера.

#### 2. Мониторинг качества (Quality & Semantic)
LLM — недетерминированные системы, поэтому классические тесты тут не работают.
- **LLM-as-a-Judge**: Использование более мощной модели (например, GPT-4o) для оценки ответов вашей модели по шкале от 1 до 10.
- **Human feedback**: thumbs up 👍 / thumbs down 👎 - можно строить графики ответов пользователей и наблюдать за динамикой реакций. В последних версиях openwebui этот график есть из коробки. 
- **Golden set запросов**: Это аналог unit-тестов для модели:
  - Есть набор эталонных запросов
  - После выката новой модели — автоматический прогон
  - Сравниваем:
    - стабильность ответа
    - семантическую близость
    - hallucination rate    

- **RAGAS Metrics** (для RAG-систем):
  - **Faithfulness**: Насколько ответ соответствует найденному контексту (нет ли галлюцинаций).
  - **Answer Relevance**: Насколько ответ вообще соответствует вопросу.
  - **Context Precision**: Насколько качественные документы нашел ретривер.
- **Sentiment & Toxicity**: Следим, чтобы модель не начала хамить или выдавать запрещенный контент (используем Guardrails).

#### 3. Дрифт данных и ответов (Model & Data Drift)
Дрифт — это когда характеристики входных данных или ответов модели меняются со временем.
- **Embedding Drift**: Мы переводим ответы модели в векторы (эмбеддинги) и сравниваем их распределение с «эталонным» (из обучающей выборки или первой недели продакшена). Если среднее расстояние между векторами растет — модель начала «уплывать».
- **Prompt Drift**: Пользователи начали задавать вопросы, к которым модель не готова (например, на другом языке или в другом стиле).
- **Prediction Drift**: Если модель внезапно стала давать слишком короткие или слишком длинные ответы по сравнению с исторической нормой.

#### Как это реализовать (Инструменты):
- **Трейсинг**: 🍀**Langfuse** , **Arize Phoenix** или **Weights & Biases**. Они позволяют видеть дерево вызовов (промпт -> поиск -> ответ) и ставить оценки.
- **Сбор метрик**: 🍀**Prometheus + Grafana** (для vLLM/Triton есть готовые экспортеры).
- **Анализ дрифта**: **Evidently AI** (отличная библиотека для визуализации дрифта в ML/LLM).

### 11. Как отслеживать, как модель переливается из оперативной памяти в GPU и обратно или прочие её тупняки?

 1️⃣ Что реально может переливаться?

Важно понимать:

❗ Веса модели обычно **один раз загружаются в VRAM** и там остаются.
Они не «прыгают» RAM ↔ GPU постоянно.

А вот что может двигаться:

#### 🔹 KV-cache

* При длинных контекстах
* При большом количестве одновременных запросов
* При `Paged Attention`
* При нехватке VRAM

Если VRAM не хватает:

* часть уходит в CPU RAM
* либо начинаются OOM / фрагментация

#### 🔹 Unified Memory (CUDA UVM)

Если включено:

* CUDA может автоматически подкачивать страницы между RAM и GPU
* Это вызывает резкие скачки latency


#### 2️⃣ Как это мониторить?

#### 🔥 A. NVIDIA уровень

#### Команда в живую:

```bash
nvidia-smi dmon
```

#### Или:

```bash
nvidia-smi --query-compute-apps=pid,used_memory --format=csv
```

#### Следить за:

* GPU memory usage
* GPU utilization
* Memory controller utilization
* PCIe RX/TX throughput

Если видишь:

* низкий GPU util
* высокая latency
* высокий PCIe трафик

→ значит данные гоняются CPU ↔ GPU

#### 🔥 B. DCGM Exporter + Prometheus

Смотреть:

* `DCGM_FI_DEV_FB_USED`
* `DCGM_FI_DEV_GPU_UTIL`
* `DCGM_FI_DEV_PCIE_TX_BYTES`
* `DCGM_FI_DEV_PCIE_RX_BYTES`

📌 Резкие пики PCIe = возможная подкачка

#### 🔥 C. vLLM метрики

vLLM отдаёт:

* KV cache usage
* Paged attention stats
* tokens/sec
* queue length

Если:

* растёт queue
* падает tokens/sec
* VRAM почти 100%

→ вероятен memory pressure

#### 3️⃣ Как диагностировать «тупняки»

Типичные симптомы:

| Симптом           | Причина                |
| ----------------- | ---------------------- |
| Высокий TTFT      | перегруженный KV-cache |
| Низкий GPU util   | bottleneck в CPU / IO  |
| Плавающая latency | page migration         |
| OOM на пиках      | фрагментация VRAM      |
| Внезапные лаги    | PCIe saturation        |

### 12. Зачем нужны и какие бывают профилировщики LLM?

**Профилировщики** в LLM — это инструменты, которые помогают понять, где тормозит inference (генерация ответов), сколько времени уходит на KV-cache, attention, память и GPU/CPU.

**Зачем в MLOps**  
- Находить bottlenecks: memory-bound vs compute-bound  
- Оптимизировать: batch size, KV-cache, quantization  
- Сравнивать движки: vLLM vs TGI vs llama.cpp  

Коротко, основные типы и примеры (2025–2026):

- **PyTorch Profiler** — самый простой, встроен в torch. Показывает timeline операций, memory, CPU/GPU. Используй в vLLM, TGI, Hugging Face.  
  Включаешь: `--profiler-config torch` при запуске сервера.

- **NVIDIA Nsight Systems / Compute** — топ для GPU. Видно CUDA kernels, memory bandwidth, stalls, launch delays. Идеально для vLLM, llama.cpp, TensorRT-LLM.  
  Самый детальный, но тяжёлый.

Пример:
```bash
nsys profile python serve.py
```

- **ProfInfer** (новинка ~2025–2026) — eBPF-based, low-overhead (<4%), не требует перекомпиляции. Смотрит operator-level (MoE routing, offloading, dense layers). Отлично для production-отладки.

- **Встроенные в движки**:
  - vLLM: свой torch profiler + --profile
  - llama.cpp: --profile / --log-disable
  - TGI / SGLang: встроенные traces

- **Другие**: Intel VTune (для CPU/Intel GPU), ELANA (энергия + latency + memory), custom GPU profilers (типа LLMTraceFX).

### 13. Для чего нужен KV-cache?
  - Ответ: **KV-cache снижает сложность вычислений при генерации следующего токена с квадратичной O(n²) до линейной O(n)**,
где n — длина уже сгенерированного текста (текущий контекст).

  [хорошая статья](https://serverflow.ru/blog/stati/chto-takoe-kv-cache-i-kak-on-uskoryaet-rabotu-yazykovykh-modeley-llm/) 

  **KV-кэш (Key-Value Cache)** — механизм оптимизации инференса LLM, сохраняющий промежуточные результаты вычислений (векторы Keys и Values) для всех обработанных токенов в памяти GPU. Это предотвращает избыточные вычисления на каждом шаге генерации, значительно снижая задержку (latency). Эффективное управление KV-кэшем (например, через PagedAttention в vLLM) является ключом к масштабированию систем с длинным контекстом.

  Более развернуто:

   **KV Cache** — это механизм кэширования промежуточных вычислений в архитектуре трансформеров, который сохраняет ключи (Key) и значения (Value) для всех предыдущих токенов во время инференса. Без KV Cache модель вынуждена была бы пересчитывать матрицы Key и Value для всей последовательности при генерации каждого нового токена, **что создавало бы квадратичную зависимость (O(n²)) между длиной контекста и требуемыми вычислениями**. **С использованием кэша сложность снижается до линейной (O(n))**, поскольку новые вычисления выполняются только для последнего токена, а для всех предыдущих используются закэшированные значения. Технически KV Cache хранит выходные значения ключей и значений для каждого слоя внимания и для каждой "головы" внимания в модели. При генерации очередного токена механизм внимания использует текущий токен как Query (запрос), а все Key и Value из кэша — для расчета весов внимания и итогового представления.  

**vLLM** внедрил одну из самых передовых реализаций — **PagedAttention**. Вместо того чтобы размещать KV-кеш непрерывно и напрямую в памяти GPU, как это делалось ранее, **vLLM** разбивает кеш на страницы фиксированного размера и создает таблицу виртуальных и фактических блоков памяти (как в классическом RAM). Это решает проблему фрагментации памяти и позволяет динамически перераспределять ресурсы между несколькими запросами. **Такое решение критично при выполнении инференса в нескольких пользовательских сессиях**. Поскольку страничный подход **поддерживает переиспользование выделенных блоков**, достигается прирост скорости до 24x относительно базовой реализации.

### 14. Что такое NVIDIA GPU Operator? 

[оф дока](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/index.html)  

Ответ: Это инструмент для управления видеокартами NVIDIA внутри кластера Kubernetes. Разворачивается как **Helm-Chart**. 
Он сам обнаруживает новые узлы с GPU и подготавливает их к работе - устанавливает драйверы, настраивает библиотеки, ставит метки с информацией о картах на ноды и вводит их в эксплуатацию. А также, собирает метрики.

**Основные компоненты:**
```bash
kubectl get pods -n gpu-operator
NAME                                                  READY   STATUS    RESTARTS   AGE
gpu-operator-7f6d9c9d8f-abcde                         1/1     Running   0          12d
nvidia-container-toolkit-daemonset-5k2lm              1/1     Running   0          12d
nvidia-device-plugin-daemonset-9x8zt                  1/1     Running   0          12d
nvidia-dcgm-exporter-2jf92                            1/1     Running   0          12d
nvidia-driver-daemonset-rtx8k                         1/1     Running   0          12d
nvidia-mig-manager-6tq4p                              1/1     Running   0          12d
```

1. **NVIDIA Driver**: Самый важный слой. Это драйвер видеокарты, который ставится через Kubernetes.
2. **NVIDIA Container Toolkit**: Мостик между контейнерами и видеокартой. Позволяет приложениям внутри Docker-контейнеров «видеть» графический процессор и использовать его мощности.
3. **Node Feature Discovery (NFD)**: «Разведчик», сканирует оборудование сервера и ставит на него метки (`labels`), сообщая оператору: «Эй, здесь есть видеокарта NVIDIA вот такой модели».
4. **NVIDIA Device Plugin**: Регистрирует видеокарты как ресурсы в кластере. Благодаря ему Kubernetes понимает, что на узле есть, например, 4 свободные GPU, и может отправить туда ваши задачи.
5. **DCGM Exporter**: Сборщик метрик. Он вытягивает данные о температуре видеокарты, загрузке памяти и энергопотреблении, чтобы вы могли видеть красивые графики в Grafana.
6. **GFD (GPU Feature Discovery)**: Дополняет метки NFD более детальной информацией — например, сообщает конкретную модель видеокарты (A100, T4) и объем видеопамяти.
7. **MIG Manager**: Полезен для мощных карт (как A100 или H200). Позволяет аппаратно «разрезать» одну физическую видеокарту на несколько независимых частей, чтобы их можно было детерменированно разделить между несколькими моделями.

### 15. Pod с моделью стартанул, но при этом модель не отвечает на запросы, в логах ошибка о том что не могут быть найдены CUDA ядра, что будешь делать?

Ответ:

> 1. Проверяю, выделен ли GPU pod'у (limits nvidia.com/gpu).
> 2. Проверяю видимость GPU внутри контейнера (nvidia-smi).
> 3. Проверяю работу device-plugin и runtimeClass.
> 4. Проверяю совместимость драйвера и версии CUDA.
> 5. Проверяю архитектуру GPU (sm_80 vs sm_90).
> 6. Если используется MIG — проверяю правильный resource request.

---

#### nvcc и nvidia-smi

nvcc (NVIDIA CUDA Compiler) — это компилятор CUDA-программ.

#### 1️⃣ `nvcc --version`

* **Что делает:** показывает версию CUDA **компилятора** (`nvcc` — NVIDIA CUDA Compiler).
* **Для чего используется:** чтобы убедиться, что код CUDA может быть скомпилирован под конкретную версию компилятора и target GPU.
* **Вывод содержит:** версию компилятора, release, build, иногда путь к toolkit.

Пример:

```
$ nvcc --version
Cuda compilation tools, release 12.2, V12.2.128
```

* Скажет, какой компилятор у тебя установлен, и под какую CUDA версию он компилирует.
* **Не показывает состояние GPU** и не мониторит запущенные процессы.

#### 2️⃣ `nvidia-smi`

* **Что делает:** показывает **текущее состояние GPU** на машине.
* **Для чего используется:** мониторинг загрузки GPU, памяти, процессов, температуры, энергопотребления.
* **Вывод содержит:** список GPU, память, GPU-Util, Perf State, процессы, температуру, power draw, версию драйвера и CUDA.

Пример:

```
+-----------------------------------------------------------------------------+
| NVIDIA-SMI 535.104.05    Driver Version: 535.104.05    CUDA Version: 12.2   |
|-------------------------------+----------------------+----------------------+
| GPU  Name            ...     | ...                  | ...                  |
| 0    A100 80GB      ...      | 73452MiB / 81920MiB | 94%                  |
+-----------------------------------------------------------------------------+
```

* Скажет, загружен ли GPU моделью, есть ли OOM, какие процессы используют карту.
* **Не компилирует код**, не показывает версии компилятора.
